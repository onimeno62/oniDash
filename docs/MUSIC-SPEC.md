# oniDash Music Specification

**Status:** Canonical Music module contract

## Purpose
Music is a complete local music manager and player inside oniDash. The module must manage the user's catalogue, files, metadata, artwork, lyrics, playback, queue, collections and listening history.

## Library model
A Music library may contain multiple source folders. The source configuration is separate from catalogue entities. Scanning is incremental and reconciles new, changed, moved and missing files.

### Core entities
- Track
- Album
- Artist
- Album Artist
- Genre
- Disc
- Music File
- Playlist / Playlist Item
- Smart Playlist
- Favorite
- Rating
- Play History
- Playback State
- Lyrics / Lyrics Version
- Artwork
- Scan Job / Operation Result

## Required library views
- Songs
- Albums
- Artists
- Genres
- Folders
- Favorites
- Top Rated
- Most Played
- Recently Played
- Recently Added
- Never Played
- Playlists
- Smart Playlists
- Missing Files
- Duplicates

All views are real database queries with server-side sorting, filtering and pagination.

## File management
The module must support explicit rename, move, delete-from-disk, remove-from-library, open-location, bulk operations and organization templates. Bulk destructive operations require validation and confirmation. Bulk organization provides a dry-run preview before execution.

## Metadata
Read/write common embedded audio metadata and preserve fields not managed by the UI. Support single and bulk editing, normalization, metadata write verification and external identification. MusicBrainz and AcoustID are optional providers. External results are suggestions with provenance/confidence and require preview-before-apply.

## Artwork
Extract embedded artwork, optionally discover local folder artwork, cache assets and track provenance. Provider artwork is optional enrichment. Missing artwork is non-fatal and visible as a health signal.

## Playback
Playback is application-scoped and survives route/page changes. Required controls: play/pause, seek, previous, next, play-next, queue, shuffle, repeat, volume, mute and output device. Persist play history and resume state. Add gapless playback, crossfade and ReplayGain as capability-based features.

## Audio
Support the formats available through the selected decoder stack. Prefer Windows WASAPI for output. Decoder, DSP, analyzer and output are separate stages. Unsupported codec/device capabilities must fail gracefully.

## Queue
Queue is a first-class persisted/in-memory player concept. Support add, play-next, remove, reorder, clear, shuffle and save-as-playlist. Queue state must not be owned by a page component.

## Lyrics
Support embedded lyrics, local `.lrc`/`.txt`, provider lookup, plain lyrics, synchronized lyrics and editing. LRCLIB is the initial provider. Synced lyrics must track playback and clicking a timestamped line seeks the player. Saving lyrics is explicit and preserves provenance/local edits.

## Visualizers
Provide waveform seeking plus audio-reactive spectrum, bars and oscilloscope visualizers. Visualizers consume analysis data generated by the active playback pipeline.

## Collections and statistics
Favorites and ratings are distinct. Ratings use a five-star scale. Persist play count and last-played time. Derived collections include Recently Added, Recently Played, Most Played, Never Played and Top Rated. Statistics should report listening time and useful playback trends.

## Context actions
Every track surface uses the same command set: Play, Play Next, Add to Queue, Add to Playlist, View Album, View Artist, Edit Metadata, Identify, Find/View Lyrics, Rename, Move, Open Location, Favorite, Rating, Track Information, Remove from Library and Delete File.

## Safety
No provider may silently overwrite local metadata. No operation may silently rename, move, delete or overwrite user media. Failed operations must be visible and recoverable.

## Completion standard
A Music capability is complete only when the backend/domain operation, API contract, UI workflow, tests and failure/loading/empty states all work together.
